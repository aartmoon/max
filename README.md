# Твой дом

Рабочий MVP-каркас для хакатона «Умный город»: житель описывает проблему ЖКХ, прикладывает фото, указывает адрес и получает обращение с категорией, ответственной организацией, сроком и историей статусов. Все действия жителя оформляются как заявки: запрос, вопрос, экстренно, проблема или жалоба. Тип выбирается внутри общей формы.

Это демонстрационный стенд: один общий тестовый пользователь, без авторизации и реального AI/ЖКХ. Приветствие MAX-бота можно включить отдельным токеном; уведомления о заявках пока mock. Все открывшие стенд видят одни и те же заявки. Кабинет УК также открыт без авторизации и работает со всеми тестовыми организациями.

## Быстрый запуск

Нужны Docker Desktop либо Docker Engine с Compose v2 и доступ к интернету для первой сборки.

```bash
docker compose up --build
```

Открыть **http://localhost:3000/max/**. Схема БД и тестовые справочники создаются backend автоматически после готовности PostgreSQL. При перезапуске backend ожидает базу до 30 секунд. Копировать `.env` для первого запуска не обязательно: есть демо-значения по умолчанию.

Для изменения параметров:

```bash
cp .env.example .env
docker compose up --build
```

Фоновый запуск: `docker compose up --build -d`. Проверка состояния: `docker compose ps`. Логи: `docker compose logs -f backend`. Остановка: `docker compose down` — данные сохраняются в томе `postgres_data`. Команда `docker compose down -v` удаляет все демо-данные, включая фотографии.

## Архитектура

```text
React + TypeScript (mobile-first, MAX-ready web app)
              │ REST /api, same origin
       nginx (frontend container)
              │
 Go modular monolith (backend container)
 controller → service → repository → PostgreSQL
                 │
           integration interfaces
           ├── MaxClient → MockMaxClient
           └── HousingSystemGateway → MockHousingSystemGateway
```

Три сервиса Compose: `frontend`, `backend`, `postgres`. nginx раздаёт собранную SPA, перенаправляет `/api` в backend и поддерживает прямое открытие вложенных страниц. CORS для этого не требуется.

Backend: стандартный `net/http`, pgx, явная передача зависимостей в `cmd/server`. `RequestService` координирует создание заявки, `AdminService` — административные переходы и комментарии; `Classifier` и `Router` заменяются независимо. `NotificationService` использует `MaxClient`. Создание обращения и начальной истории атомарно; смена статуса использует транзакцию и блокировку строки.

## Пользовательский сценарий

1. Открыть главную страницу `/`.
2. Выбрать «Создать заявку», затем внутри формы выбрать тип: «Запрос», «Вопрос», «Экстренно», «Проблема» или «Жалоба».
3. На `/requests/new` заполнить описание (5–5000 символов), указать адрес (5–300 символов) либо оставить тестовый: `г. Москва, ул. Тестовая, д. 1`.
4. При желании приложить JPEG, PNG или WebP до 5 МиБ. Фото проверяется по содержимому и сохраняется в `bytea` PostgreSQL; хранилище файлов для MVP не требуется.
5. Нажать «Продолжить»: форма показывает загрузку, ошибки сохраняют введённые данные.
6. На `/requests/:id` увидеть категорию, ответственного, статус, срок, текст обращения, фото и историю.
7. Открыть `/admin`, выбрать заявку и изменить статус с комментарием для жителя. Старые демо-кнопки жителя также сохранены.
8. В `/requests` открыть сохранённые обращения. Перезагрузка страницы и перезапуск контейнеров данные не удаляют.

Начальный статус — **CREATED / Создано**. Демо-цепочка:

```text
CREATED → SENT → ACCEPTED → IN_PROGRESS → RESOLVED
```

`REJECTED` доступен отдельной демо-кнопкой из любого незавершённого статуса. `RESOLVED` и `REJECTED` терминальные; дальнейший переход возвращает 409.

Срок — **3 календарных дня от создания**, исключительно демонстрационный, не нормативный срок ЖКХ.

## Mock-логика

Правила проверяются по порядку, без учёта регистра, `ё` приравнивается к `е`:

| Подстроки описания | Категория | Ответственный |
| --- | --- | --- |
| `труба`, `течёт` / `течет`, `протечка` | `PIPE_LEAK` | УК «Тестовая» |
| `лифт` | `ELEVATOR` | УК «Тестовая» / подрядчик «ТестЛифт» |
| `отопление`, `батарея`, `холодно` | `HEATING` | УК «Тестовая» |
| Всё остальное | `OTHER` | УК «Тестовая» |

Это поиск подстрок, не морфологический анализ. Текст обращения формируется шаблоном. Произвольный адрес сохраняется как дом, но маршрутизация пока не использует реальные реестры.

`MockMaxClient` записывает событие уведомления в лог. `MockHousingSystemGateway` имитирует отправку при статусе `SENT`. Frontend загружает официальный MAX Bridge асинхронно; в обычном браузере используется `BrowserBridge` без вызовов нативных методов. Для веб-демо токен не требуется; для ответов чат-бота на `/start` настройте переменные ниже.

## REST API

| Метод | Путь | Результат |
| --- | --- | --- |
| POST | `/api/requests` | 201: созданное обращение |
| GET | `/api/requests` | Массив обращений общего демо-пользователя |
| GET | `/api/requests/{id}` | Карточка |
| GET | `/api/requests/{id}/history` | История от старого статуса к новому |
| GET | `/api/requests/{id}/photo` | Изображение или 404 |
| POST | `/api/requests/{id}/mock-next-status` | Следующий статус |
| POST | `/api/requests/{id}/mock-next-status?reject=true` | Отклонение |
| GET | `/api/health` | Готовность сервера и БД |
| GET | `/api/config` | Доступность демо-переходов для UI |

JSON без фото:

```bash
curl -X POST http://localhost:3000/max/api/requests \
  -H 'Content-Type: application/json' \
  -d '{"description":"В подъезде течёт труба","address":"г. Москва, ул. Тестовая, д. 1","kind":"PROBLEM"}'
```

С фото:

```bash
curl http://localhost:3000/max/api/requests \
  -F 'description=Не работает лифт' \
  -F 'address=г. Москва, ул. Тестовая, д. 1' \
  -F 'kind=PROBLEM' \
  -F 'photo=@/path/to/photo.jpg'
```

`kind`: `APPLICATION` (по умолчанию, «Запрос»), `QUESTION` («Вопрос»), `EMERGENCY` («Экстренно»), `PROBLEM` («Проблема»), `COMPLAINT` («Жалоба»). Старые типы и ссылки поддерживаются. Ответ содержит обязательные поля Request, а также `address`, `responsibleOrganization`, `kind`, `text`, `hasPhoto`. Даты — ISO 8601, идентификаторы — строки. `userId` и ответственный назначаются сервером.

Ошибки API: JSON `{"error":"сообщение"}`; 400 — валидация/некорректный ID, 404 — нет обращения или фото, 409 — терминальный статус, 413 — HTTP-запрос больше 6 МиБ, 415 — неподдерживаемый Content-Type, 500 — внутренняя ошибка. nginx также ограничивает тело запроса 6 МиБ.


## Кабинет УК и подрядчиков

Открыть **http://localhost:3000/max/admin** или ссылку «Кабинет УК» в шапке. Рабочая очередь показывает активные, новые, находящиеся в работе, просроченные и завершённые заявки. Доступны полнотекстовый поиск, фильтры по организации, типу и статусу, а также сортировка по приоритету, сроку или дате создания. Экстренные и просроченные заявки автоматически поднимаются выше. Состояние фильтров сохраняется в URL, поэтому ссылкой на нужную выборку можно поделиться.

В `/admin/requests/:id` доступны описание, фото, история и изменение статуса с комментарием. Допустимые переходы кабинета:

- `CREATED` / `SENT` → `ACCEPTED` или `REJECTED`;
- `ACCEPTED` → `IN_PROGRESS` или `REJECTED`;
- `IN_PROGRESS` → `RESOLVED` или `REJECTED`.

При отклонении обязательна причина, а при завершении — описание результата; комментарий ограничен 2000 символами. Комментарий и автор `УК · демо` сохраняются в истории вместе со статусом и видны жителю после открытия/обновления карточки. Завершённые заявки не редактируются. Экстренный тип выделяется в очереди, но не вызывает реальные аварийные службы и пока имеет общий демонстрационный срок 3 дня.

Административные API:

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/admin/requests` | Все заявки всех демо-пользователей |
| GET | `/api/admin/requests/{id}` | Детали |
| GET | `/api/admin/requests/{id}/history` | История с `comment` и `actor` |
| GET | `/api/admin/requests/{id}/photo` | Фото |
| PATCH | `/api/admin/requests/{id}/status` | JSON `{"status":"ACCEPTED","comment":"Мастер назначен"}` |
| GET | `/api/organizations` | Справочник организаций |
| POST | `/api/houses/resolve` | Выбор дома по GAR object ID и паспорт из ГИС ЖКХ |

Административные API работают независимо от `MOCK_STATUS_ENABLED`: этот флаг выключает только старые демо-кнопки жителя. Кабинет сейчас не защищён входом; перед реальным запуском необходимо добавить проверку роли УК и ограничение заявок организацией. Фильтр организации в UI не является контролем доступа.

## Мой дом

Открыть **http://localhost:3000/max/house** и выбрать адрес из локального справочника ГАР. В браузере сохраняется только GAR object ID выбранного дома. Backend по FIAS/GAR GUID обращается к публичным JSON-ручкам реестра ГИС ЖКХ, нормализует доступные характеристики и сохраняет успешный ответ в PostgreSQL на 24 часа.

Если отдельное поле не опубликовано, интерфейс показывает «Нет данных». При временной недоступности ГИС ЖКХ возвращается последний кеш с предупреждением об устаревании; если кеша нет, пользователь получает явную ошибку вместо тестового паспорта. Старый `GET /api/house` удалён. Доступ к закрытому SOAP API, сертификаты и учётные данные не используются.


## MAX-бот: /start → приложение

Встроен реальный клиент MAX Bot API. Бот отвечает на `/start`, `/start <параметры>` и событие `bot_started` (кнопка «Начать»). При заданном username также понимает `/start@username`. Ответ: приветствие и кнопка «Перейти на сайт»; если задан `MAX_BOT_USERNAME`, добавляется «Открыть «Твой дом»» типа `open_app`. Обычные сообщения и сообщения ботов игнорируются; текстовые команды обрабатываются в личном диалоге.

Настройка в корневом `.env` (не отправляйте токен в чат и не коммитьте его):

```dotenv
MAX_BOT_TOKEN=вставьте_свой_токен
MAX_APP_URL=https://ваш-публичный-домен
# Необязательно; только после настройки мини-приложения у бота в MAX:
MAX_BOT_USERNAME=имя_вашего_бота_без_собачки
```

1. Скопировать `.env.example` в `.env`, если файл ещё не существует; существующий `.env` не перезаписывать.
2. Указать токен и публичный HTTPS-адрес приложения. Для разработки подходит HTTPS-туннель на порт 3000. `localhost` и частный IP с телефона не работают; код отклоняет такие значения. Публикация сайта/создание туннеля не входит в эту интеграцию.
3. Для нативного мини-приложения привязать публичный адрес сайта к боту в MAX для бизнеса, затем указать `MAX_BOT_USERNAME`. Здесь нужен username бота, а не URL сайта. Если оставить поле пустым, будет только кнопка-ссылка на сайт.
4. Выполнить `docker compose up --build -d`. Compose передаёт значения из `.env` только backend; Go при запуске вне Compose читает переменные процесса, а не файл `.env` автоматически.
5. Открыть личный диалог с ботом и отправить `/start`. Проверить логи: `docker compose logs -f backend`. При пустом токене бот отключён. Токен не выводится в логах и отсутствует в браузерной сборке.

Используется [официальный MAX API](https://dev.max.ru/docs-api), домен `platform-api2.max.ru`, токен в заголовке Authorization. [Long polling](https://dev.max.ru/docs-api/methods/GET/updates) подходит для разработки и не требует доступного извне backend. Для production MAX требует webhook. Если у бота уже есть webhook-подписка, long polling недоступен: удалите её отдельно либо используйте другой тестовый бот. Код не удаляет существующие подписки и не изменяет настройки бота автоматически.

Один токен должен обслуживаться одним экземпляром backend. Маркер хранится в памяти; при перезапуске возможно повторное приветствие на последнее событие. Временные ошибки сети/429/5xx повторяются с задержкой, неуспешное событие не продвигает маркер до обработки. Постоянная ошибка отправки (например, пользователь заблокировал бота) фиксируется без текста ответа API и пропускается; ошибка авторизации останавливает бот до исправления токена и рестарта. HTTP-приложение при этом продолжает работать. Доставка приветствий здесь не является гарантированной очередью сообщений.

MAX отдельно указывает на необходимость доверенного сертификата Минцифры. Если системного хранилища недостаточно и в логах ошибка сети/TLS, положите официальный доверенный PEM в `certs/max-ca.pem` и задайте `MAX_CA_CERT_FILE=/app/certs/max-ca.pem`. Compose монтирует папку только для чтения. Сертификат добавляется к системным корням; проверка TLS не отключается. Подробнее в `certs/README.md`.

Это только вход в приложение: привязки MAX-пользователя к жителю пока нет. `NotificationService` всё ещё использует mock, чтобы тестовый `userId=1` не стал получателем реальных сообщений. Бот не делает реальную отправку заявок в ЖКХ.

Проверка без токена: `cd backend && go test ./integration/maxbot`. Тесты используют локальный HTTP-сервер, проверяют `/start`, `bot_started`, кнопки, авторизацию заголовком, обработку ошибок, маркер и отмену polling. Реальная доставка в MAX проверяется после заполнения `.env` пользователем.


## MAX Bridge в мини-приложении

Официальный SDK `https://st.max.ru/js/max-web-app.js` загружается асинхронно из `integration/max.ts`. Интерфейс отображается независимо от скорости CDN. При загрузке SDK выбирается `NativeMaxBridge`, если присутствует `WebApp.initData`; в обычном браузере и при ошибке загрузки работает `BrowserBridge`. Поздняя загрузка SDK также подключает нативные функции.

- `ready()` вызывается после первого отображения React, один раз на экземпляр адаптера.
- Кнопка MAX «Назад» видна на вложенных страницах. Переход возвращает на предыдущий экран приложения, а при прямом входе — к родительскому разделу. На главной кнопка скрыта; обработчики снимаются при смене страницы.
- Для заполненной формы заявки включается `enableClosingConfirmation()`, при очистке/уходе с формы — выключается. Это подтверждение закрытия всего mini app, не блокировка внутренних переходов.
- `launchData()` предоставляет raw `initData`, платформу и `start_param` в памяти. Данные не сохраняются в localStorage, не логируются и не используются как авторизация.
- Поддержаны стартовые значения `house`, `requests`, `new_request`: например, `https://max.ru/имя_бота?startapp=house`. Они открывают «Мой дом», список или форму соответственно. Неизвестные значения игнорируются; произвольные URL и кабинет УК через этот параметр не открываются. Параметр применяется только при начальном входе на главную, не прерывая уже начатую навигацию.

Серверная проверка подписи `initData` и привязка жителя по-прежнему не реализованы: авторизация не входила в MVP. Для реального доступа пользователей это отдельный обязательный этап. Данные `initDataUnsafe` используются только для выбора стартового экрана.

Браузерные тесты `tests/max-bridge.spec.ts` имитируют контракт официального SDK: загрузку, ready после рендера, нативную навигацию, защиту закрытия формы, позднюю загрузку и недоступность CDN. Проверка на настоящем устройстве MAX требует опубликованного HTTPS-сайта и привязанного к боту мини-приложения.

## Разработка и тесты

### Адреса ГАР/ФИАС

Одноразовый сервис `gar-init` используется только для первичной загрузки GAR.
На production он потоково импортирует XML из `${GAR_XML_PATH:-/home/user1/gar/xml}`.
После успешной загрузки обычный deploy его не запускает. Локально
можно оставить каталог `gar-data/` пустым: Compose явно разрешает небольшой
набор связанных тестовых адресов, домов и квартир.

```bash
# Первый запуск production:
docker compose -f docker-compose.prod.yml --profile init up gar-init

# Обычный production deploy:
./deploy.sh

# Локальная разработка:
docker compose up --build gar-init
docker compose up --build -d
docker compose logs -f gar-init
```

Форма новой заявки ищет дома через `GET /api/addresses/search`, затем при
необходимости загружает квартиры выбранного дома. В заявку передаются GAR
`houseObjectId` и необязательный `apartmentObjectId`; backend заново проверяет
объекты и сохраняет полный адрес из базы, а не введённую пользователем строку.

Подробная инструкция по первому импорту, проверке количества строк и безопасному
перезапуску: [`gar-init/README.md`](gar-init/README.md).

Локально нужны Go 1.24+ и Node.js 22 с pnpm 11.19.0. Рекомендуемые версии для воспроизводимой сборки заданы Dockerfile и lock-файлами.

```bash
docker compose up -d postgres
# В другом терминале:
cd backend
export DATABASE_URL='postgres://tvoydom:tvoydom_demo@localhost:5433/tvoydom?sslmode=disable'
go run ./cmd/server
# В третьем терминале:
cd frontend
pnpm install --frozen-lockfile
pnpm dev
```

Локальный Vite открывается на 5173 и проксирует `/api` на localhost:8080.

Проверки:

```bash
cd backend
go test ./...
go vet ./...
cd ../frontend
pnpm build
# При запущенном Compose:
pnpm exec playwright install chromium
pnpm test:e2e
cd ..
python3 scripts/smoke.py
```

Тесты создают отдельные демо-обращения в запущенной БД. Удаление не выполняется автоматически. `API_URL` меняет адрес smoke-теста; `BASE_URL` — Playwright.

## Подключение MAX и реальных ЖКХ-систем позже

1. Разместить приложение на публичном HTTPS-адресе и настроить открытие mini app в MAX согласно [официальной документации](https://dev.max.ru/docs/webapps/introduction). Этот репозиторий не регистрирует приложение в MAX и не публикует его автоматически.
2. MAX Bridge уже подключён: SDK, `ready()`, нативная кнопка «Назад», стартовые параметры и подтверждение закрытия заполненной формы. Проверьте их работу внутри зарегистрированного мини-приложения.
3. Адаптер приветствия чат-бота уже реализован отдельно в `integration/maxbot`. Для уведомлений о заявках реализовать backend `MaxClient` и передать его при сборке зависимостей. Токены держать только на сервере. Перед использованием реального пользователя добавить проверку подписанных параметров MAX и заменить `DemoUserID`; авторизация выходит за рамки текущего этапа.
4. Реализовать `HousingSystemGateway` для конкретной системы и подставить в `RequestService`. Сейчас вызов синхронный и mock всегда успешен. Для реальных отправок потребуется надёжная доставка, повторные попытки и сопоставление внешних статусов; нельзя считать лог mock подтверждением доставки. Это можно сделать в монолите с PostgreSQL, без новой инфраструктуры.
5. Заменить `RuleRouter` адаптером справочника домов и организаций, `RuleClassifier` — другой реализацией `Classifier`, когда появится потребность. Текстовый шаблон и правила срока находятся в `service/request.go`.
6. Добавлять дальнейшие версии в `repository/migrations` и подключать их в `Postgres.Migrate`. Версия 2 уже обновляет существующие заявки и паспорт дома без потери фото. Версия отмечается в `schema_migrations`; схема и миграция применяются одной транзакцией с блокировкой от параллельного запуска.

В MVP нет микросервисов, Kafka, Redis, Kubernetes, Elasticsearch или LLM. Проверка внутри реального MAX требует регистрации приложения и HTTPS; браузерный демо-режим работает без них.
